### 컨테이너 기술의 필요성

- VM에서는 OS와 instruction set까지 가상화
→ 성능저하 + 추가 오버헤드가 따라온다.
- 실행되는 애플리케이션들을 보아 하니, OS와 instruction set에는 크게 다르지 않더라. 
(다 linux 배포판을 쓰며 instruction set은 arm/x86 정도의 차이)
- 근데, 애플리케이션이 **의존하는 라이브러리나 소프트웨어의 버전은 다 제각각**이고 다르면 애플리케이션이 잘 안 돌아가더라.

→ 커널(OS) 는 공유하고, 애플리케이션들이 **각자 돌아가는 환경만** 격리시키자.

#### 컨테이너에선 무엇을 격리시켜야 하나요?

컨테이너별로 격리된 파일 시스템을 가지게 하는 간단한 방법으로 `chroot`이 있다.

- `chroot`(change root): 특정 프로세스가 보이는 루트 디렉터리를 특정 디렉터리로 지정한다.
1. 특정 용도에 필요한 환경 전체(디렉터리들 + 라이브러리 + 실행파일)를 싹 복사한다.
2. 특정 디렉터리에 붙여넣는다.
3. `chroot` 등의 명령어로 특정 프로세스가 그 디렉터리를 루트 디렉터리로 인식하게 한다.

이 방식의 문제점은?

1. 다른 컨테이너에서 실행되는 애플리케이션의 **프로세스가 격리되지 않음**
    - 보안 문제 (e.g. 만약 컨테이너 내부에서 다른 프로세스를 안다 → 동일 linux user라면 sigkill 가능)
    - 컨테이너 단위의 프로세스 제어가 안 됨
        - 컨테이너 내부 모든 프로세스는 종료(sigkill)될 수 있어야 함
        - 컨테이너에서는 내부 프로세스를 격리하고, 여기서 처음 시작하는 프로세스가 컨테이너 안에서의 PID 1이 된다.
        - 컨테이너의 PID 1에 sigkill/sigstop을 보내면 컨테이너 내부의 모든 프로세스가 종료된다.
        커널은 컨테이너 내부의 모든 프로세스에게 sigkill을 보내 종료시켜 컨테이너 단위의 종료를 보장한다.
2. 여러 애플리케이션이 **같은 라이브러리를 사용하는 경우** 불필요한 복사와 공간 낭비 발생
3. 컨테이너를 호스팅하는 OS는 컨테이너들의 **자원 사용량(cpu, 메모리 사용량)을 통제하지 못함**.
    - linux에서는 프로세스별로 자원 통제는 가능하다.
        - e.g. ulimit(스택 size 최댓값), nice(스케줄 빈도 조절)
    - e.g. API 서버가 자기 프로세스를 fork해서 클라이언트 요청을 받는 경우
    - 스케줄러의 스케줄링은 프로세스 단위로 일어나므로, fork()를 많이 하면 내 컨테이너의 프로세스가 더 많이 스케줄링될 것이므로 이는 불공평하다.
    - 메모리도 동일하게, 프로세스별로 통제 가능하나(ulimit 등으로) fork 하면 무용지물이다.

### 컨테이너의 핵심 세가지 기술

위의 문제점으로 인해 linux에서 제공하는 **namespaces**, **cgroups**, **union filesystem** 세 가지 핵심 기능을 사용하여 컨테이너에서의 격리가 이루어진다.

![](/assets/img/컨테이너-1/image.png)

- **namespaces**
    - 컨테이너가 사용하는 **여러 리소스에 대한 격리를 제공**한다. 
    즉, **컨테이너 안 프로세스가 보는 세상을 바꿔치기**해준다.
    e.g. PID namespace: 이 컨테이너 내부에서 ps 했을 때는 PID 1 프로세스로 보이나,
    OS 입장에선 평범한 자식 프로세스가 된다.
    - 여러가지 namespace의 종류
        
        
        | 네임스페이스 | 무엇을 격리하나 |
        | --- | --- |
        | Mount (mnt) | 파일시스템 마운트 뷰 (자기만의 루트) |
        | PID | 프로세스 ID 공간 (자기만의 init) |
        | Network (net) | 네트워크 인터페이스, IP, 포트 |
        | UTS | 호스트네임, 도메인명 |
        | IPC | 프로세스 간 통신 자원 |
        | User | UID, GID (컨테이너 root ≠ 호스트 root) |
        | Cgroup | cgroup 계층의 뷰 |
        | Time | 부팅 시각 등 |
- **control groups**: 컨테이너가 사용하는 자원(cpu, memory, storage)의 제어를 위한 것.
컨테이너를 만들 때 섞이지 않도록 독립적으로 설정해줄 수 있다.
    - 각 컨테이너의 프로세스들은 하나의 색으로 묶여있고, 프로세스 하나하나가 아닌 그룹 전체에 제한이 걸린다.
    
    ![](/assets/img/컨테이너-1/image-1.png)
    
- **union filesystem**: 공유하는 파일(read-only 이미지 레이어)과 컨테이너별 writable layer
를 하나의 파일 시스템처럼 겹쳐서(union) 보여주는 기능.
컨테이너에서 공유 파일을 수정하게 되면, copy-on-write 방식으로 자기 writable layer로 복사되서 수정,
원본 레이어는 유지되어 다른 컨테이너에 영향을 미치지 않는다.
    
    ![](/assets/img/컨테이너-1/image-2.png)
    
    - 이는 mount를 여러번 함으로써 (”stacking” 함으로써) 구현된다.
        - 다만 일반 마운트와 다른 점은 overlay 타입으로 마운트된다. 즉, 신규 내용과 겹치는 것만 새로 마운트한 게 이기며 신규 내용이 아닌 기존 파일시스템의 요소는 그대로 예전 버전으로 보인다.
    - e.g. 많은 컨테이너가 ubuntu 24.04 + 신버전 php를 공유하는 상황, 특정 컨테이너가 구 버전 php가 필요한 상황
        - 이런 경우, ubuntu 24.04 + 신버전 php라는 읽기 전용 레이어에 구 버전 php를 추가로 마운트하여, 그럼 신 버전의 php는 가려지고 구 버전 php를 해당 컨테이너가 사용 가능하다.
